# 前端静态资源 Hash 机制详解

在现代前端工程化（Webpack, Vite, Rollup）中，打包生成的 JS、CSS、图片等文件名通常带有类似于 `index.d3f1a9.js` 的字符。这被称为 **文件指纹 (File Fingerprinting)**。

## 1. 核心作用：解决缓存冲突

这是引入 Hash 最根本的原因。

### 场景 A：不使用 Hash（覆盖式发布）
1. 用户访问 `index.js`，浏览器将其缓存。
2. 开发者修改了代码并部署，文件名仍为 `index.js`。
3. 用户再次访问，浏览器检测到 URL 没变，直接读取本地缓存。
4. **结果**：用户无法看到更新，除非手动清理缓存或等待缓存过期。

### 场景 B：使用 Hash（非覆盖式发布）
1. 用户访问 `index.a1b2.js`，浏览器缓存之。
2. 开发者修改代码后打包，文件名变为 `index.c3d4.js`。
3. HTML 中的引用自动指向新文件名。
4. **结果**：浏览器发现 URL 变更，立即下载新资源，实现**秒级实时更新**。

---

## 2. Hash 的三种类型对比

在配置打包工具（如 Webpack）时，理解这三种 Hash 的区别至关重要：

| 类型 | 作用域 | 触发更新机制 | 最佳实践 |
| :--- | :--- | :--- | :--- |
| **hash** | 整个项目 | 只要项目里有一个文件改变，**所有**文件的 Hash 都会变。 | 基本不再使用，缓存命中率极低。 |
| **chunkhash** | 代码分片 (Chunk) | 基于入口文件。若 A 页面引用的组件变了，只有 A 页面的 JS 会变。 | 适用于 JS 文件的打包。 |
| **contenthash** | 单个文件内容 | **最精细控制**。仅当该文件内容变化时，Hash 才会变。 | **推荐使用**。即使 JS 变了，只要 CSS 没变，CSS 缓存依然有效。 |

---

## 3. 部署稳定性与平滑过渡

使用 Hash 文件名可以实现**“版本共存”**。

在部署新版本时，旧的 `index.old.js` 和新的 `index.new.js` 可以同时存在于服务器或 CDN 上。
